# 审阅页：后台构建计划、哈希内容键（2026-10-19）

修改前，打开审阅页和确认提交都在界面线程上同步完成。打开时要构建整个审阅计划；演示模式下还要校验全部资源。确认提交时要先重建一次计划，再对新旧两份计划各做一次整份 JSON 序列化，比较两者是否一致。5 万项变更时，确认框出现前界面冻结约 1.8 s。本次修改：

- **内容键**改为 SHA-256。覆盖的内容与原 JSON 相同：阻止原因、变更类型、前后字段、标识、原始 JSON、字段意图、依赖、处置和原因。每个值都带长度前缀，因此不同内容不会因为拼接方式相同而得到同一个键。字节先写入 64 KB 缓冲区，再整块送入哈希；逐个值调用原生哈希的开销比哈希本身还大。共享的阻止原因对象只序列化一次（演示模式下，同一个阻止原因会标在每一项上）。每份计划只计算一次内容键，结果缓存在计划对象上。
- **构建计划**：在界面线程上只采集模式、已验证操作和 API 会话；计划和内容键都在后台线程上构建。期间锁定导航、工作区、资源切换和数据编辑，与原有“本地操作”使用同一个锁，并支持嵌套：外层本地操作结束时，如果后台仍在读取工作区，由后台任务负责解锁。审阅页先显示“正在整理审阅清单…”，计划完成后再填入内容。
- **确认提交**：在后台重建当前计划；已显示计划的键在构建时已经算好，比较只需要比较两个字符串。判定规则不变：内容或提交条件有变化时刷新清单，并要求重新审阅。

# 切换时复用数据页（2026-10-19）

上一步之后剩下的增长是原生内存：每重建一次数据页约 10 MiB，WinUI 不再归还。现在切换工作区或资源时不再重建数据页，只更换内容：

- **页面**：工具栏、命令栏、表格、分页栏都保留。`RebindDataPage` 换上当前工作区／资源的状态（搜索、筛选、排序列表、表头、每页条数、页码），然后清空行，等待查询结果。分页栏和表格的 Loaded 回调不再捕获某一个工作区的状态，改为读取当前显示的状态。航队分配和退役命令始终存在，按资源显示或隐藏。只有切换表格密度时才重建页面，因为行高写在行容器样式里。
- **行**：行池在列和密度不变时跨工作区、跨资源保留。单元格闭包经由 `RowLink`（工作区、资源数据、资源类型）访问数据，换数据时只改这个链接，旧行模型原地重新绑定。表头只在列变化时重建。
- **ItemsSource**：仍是普通 List，行数不变时不替换（与翻页相同）。曾试过改用可观察集合，让行数变化时也回收行容器：资源切换的原生增长能再减半，但任何可观察的 ItemsSource（包括只发 Reset 的自定义集合）都会让翻页和切换语言的布局时间翻倍（P95 10 → 20 ms、25 → 56 ms），所以没有采用。

切换工作区前的 `Save()` 每次都把整个工作区写一遍。按代码中的约定，除了单元格编辑，其他改动发生后都会立即完整保存；所以切换时其实只需要保存待写的单元格编辑（`SaveEdits`）。改成这样能去掉这部分增长，切换也会更快。但如果某处改动违反了这个约定，切换时就会丢失数据，所以这次没有改，需要单独决定。

# 切换工作区后的内存（2026-10-19）

`test-baseline-ui.ps1` 做 5 轮切换往返（大工作区 → 空工作区 → 大工作区）后，强制 GC 后的工作集从约 550／720 MiB 涨到约 1.1／1.5 GiB。增长分为两部分：

**GC 保留的已提交内存（主要部分，已修复）。** 旧 Workspace 被替换后不会马上回收。数据页每个单元格模型的编辑闭包捕获了 `owner`（Workspace）和 `source`（ResourceData）。页面被替换后，这些模型只被 WinUI 原生树和终结队列持有。用 dotnet-dump 查看切换后的堆，到达旧 Workspace 的路径全部是：终结队列中的 CsWinRT 事件源（x:Bind 的 DataContextChanged）→ `DataTableTemplates_obj8_Bindings` → `CellViewModel` → `Func<string>` → `ShowDataPageRows` 的闭包 → Workspace。这条引用要经过几轮 GC、终结器和 WinUI 延迟释放才会断开，所以切回大工作区时，`store.Load` 读出的新副本和旧副本同时存在。强制 GC 后托管堆有时翻倍（20k 118 → 230 MiB，50k 280 → 559 MiB）。GC 为这些峰值提交的内存之后不再归还：5 轮后 GC 已提交内存在 20k 为 156 → 568 MiB，在 50k 为 332 → 961 MiB，而实际存活的托管对象只有 120／284 MiB。这不是永久泄漏，20 轮往返中托管堆不累积；但工作集上涨的大部分来自这里。

其余可疑点逐一查过：`dataStates` 的 Baseline 在每次保存时清空，而切换前总会保存，所以不持有旧实例；`changeCounts` 同理；`settingsPages` 和 UiLocalization 绑定不引用工作区。会在切换后继续引用旧实例的有：`pageRowPool`、`tableBaseline`、`dataPageOwner`、`tasksOwner`／`taskModels`，要等到下次打开数据页或任务页才更新；`apiSessions` 中旧工作区的 `OperationsAdapter` 持有创建它时的实例，要等到切回该工作区才移除。

修改：

- 单元格闭包不再直接捕获 Workspace／ResourceData，改为经由每个行池共用的 `RowLink` 访问。切换工作区时 `RowLink` 被清空，已经脱离界面但尚未回收的旧页面就无法再到达数据。
- `Render` 发现 Workspace 实例变了（切换、新建、演示工作区、失败后重新读取）时，调用 `ReleaseWorkspaceViews`：清空上述缓存，解除旧表格的 ItemsSource，并释放旧工作区的 API 会话。
- QA 的 `memory` 命令新增 `committedBytes`（GC 已提交内存），用于区分 GC 保留的内存和原生内存。下表的“原生”＝私有字节 − GC 已提交。

# 表格单元格轻量化（2026-10-19）

数据页单元格改动如下：

- **显示**：平时只显示文本（`EditableCell`：一个带边框的 TextBlock）。点击、Tab 进入，或 UIA 写值时，才创建 TextBox；焦点离开、按 Enter 或 Esc 后移除 TextBox。
- **绑定**：行模板和单元格模板改为编译在 `DataTableTemplates.xaml` 中的 `x:Bind`，不再在运行时用 XamlReader 加载使用 `{Binding}` 的模板。

# 撤销／重做后只刷新受影响的行（2026-10-19）

上一节的行级保存之后，撤销仍会让所有数据页失效，并对全部数据重新查询。现在，只替换已有行的撤销或重做保留当前已应用的查询结果，不再重新查询，处理方式与单元格编辑相同。具体做法：

- 只把当前页上受影响的行重新绑定到新的行对象。
- 已修改计数按这些行的前后状态增量调整，选择计数在下次读取时重算。
- 结果中的顺序、筛选和搜索命中，等下次应用查询时再调整。

数据页状态已经不是最新时（例如查询被取消），仍会失效并重新查询。新增、删除或重排行的步骤仍完整保存，并重新查询。

另外，四类只记录任务或连接状态、不改动任何行的保存，不再让数据页失效：连接 API、加入提交任务（API 和演示）、导出 CSV、重试失败项。之后回到数据页时，不再重新查询全部数据。

# 撤销／重做改为行级保存（2026-10-19）

撤销或重做的步骤如果只替换已有行（单元格编辑、批量规则、机型分配等，行的增删和顺序都不变），现在只保存这些行，以及撤销／重做栈的顺序。被移动的步骤本身不变，不重写。保存仍走原有的单元格自动保存路径：同一事务内检查版本号，保存失败时恢复待保存记录，并让下一次改为完整保存。新增、删除或重排行的步骤仍然完整保存。撤销栈或重做栈为空时，不保存任何内容。

同一台机器上，用同一个 `test-data-performance-ui.ps1` 流程比较修改前的 QA 构建（`artifacts/ui-baseline/qa-build`）和修改后的 QA 构建（`artifacts/ui-undo/qa-build`）。计时从点击按钮对应的处理开始，包括历史移动、保存、全数据查询和布局。每组预热 5 次、采样 20 次：

# 判重索引修复与性能验证（2026-09-22）

本次承接第五轮性能优化，并修复后续复核确认的缓存生命周期及未知机场别名问题。以下为本地模拟和合成基准，不代表真实 API 联调。

## 当前行为

- 机场、机型、飞机采用执行级远端 ID 字典和签名到 ID 集合的反向索引；机场索引响应中的 ICAO、IATA，机型按名称、飞机按注册号，使用 OrdinalIgnoreCase。同签名多个 ID 全部保留，飞机仍跨全部机型。
- 完整分页读取成功才发布索引；失败后重新读取，不复用部分集合。确认创建、修改和永久删除同步更新索引；确认改名移除旧签名，保留仍使用该签名的其他实体。
- 同批确认结果和未知写入使用独立签名索引。未知修改保留前后签名，未知删除不释放原签名。命中不确定身份的新增保持 Pending，显示待核对原因。
- 机场创建未核对成功时，后续机场创建均保持 Pending，包括已返回 ID 但尚未完成回读的情况。其他独立资源继续执行；输入候选 ID、空列表或核对失败不会解除保护。
- 每次恢复重建未知预留，已成功记录不重发。确认候选重新从 API 读取，不以旧成功任务的本地快照初始化；兼容缺少 RawApiJson 的历史成功记录。
- 航线、航路仍按远端机场对 ID 查询候选，完整分页并本地精确判重。机场删除四路 OR 引用查询、机型依赖筛选保持不变。
- 数据库结构、关键落盘屏障、CSV 格式、API 请求体、限流及能力禁用条件不变。增量保存和任务页局部刷新不在本轮范围。

## 索引基准

合成 20,000 条机型记录，进行 100 次确认改名；每次分别查询原名、新名、已释放旧名及不存在的名称，共 400 次查询。每个返回候选均调用实际 IsDuplicate 精确比较。

| 指标 | 结果 |
|---|---:|
| 完整列表读取 / 成功索引构建 | 1 / 1 |
| 查询次数 | 400 |
| 实际精确比较候选 | 200 |
| 确认改名引发额外列表读取 | 0 |
| 本次构建及查询测量耗时 | 207.1 ms |
| 测量期间托管分配 | 63,055,528 字节 |

构建复杂度与记录数成正比，后续查询只枚举匹配的 ID 集合；不再每次遍历两万行。时间包含首次模拟响应解析、索引构建和循环查询；预制响应生成不计入。分配使用 GC.GetTotalAllocatedBytes，表示累计托管分配，不能解释为峰值或常驻内存。单次本机测量受 JIT、GC 和缓存影响，不作为跨机器性能保证，也不包含真实网络、UI 或 SQLite 写入。

## 请求量与保存基准

已有两万条航线、100 条新增且机场对候选稀疏：判重 GET=100、POST=100、回读 GET=100，共 300 次业务请求；虚拟时间为 299 秒。保留密集机场对的多页测试，不把一次 GET 当作所有 VA 的上限。

SQLite 合成保存仍使用全工作区 JSON；零撤销 / 三份撤销分别为 24,916,345 / 62,289,714 字节，序列化约 187.8 / 300.5 ms，SQLite 保存约 116.4 / 267.4 ms。每组一次。此结果与 API 请求基准独立测量，不能相加作为端到端耗时；JSON 字节不是物理 WAL 写入量。

机器可读结果：`artifacts/index-fix-20260922/benchmark/benchmark.json`。

## 指标与复现

在线任务结束后尝试保存 `performance/<workspace-guid>/<job-guid>/<run-guid>.json`，默认位于 `%LOCALAPPDATA%/VamSysBatch`，也遵循 VAMSYS_DATA_DIR。

- Requests 按资源、执行阶段、HTTP 方法统计；OAuth 单独统计。Retries、Pages 统计实际重试和解析成功的页面。
- Candidates 统计实际精确比较或依赖检查的候选；IndexBuilds 只统计完整建立并发布的判重索引，不把同批确认结果的小型索引计为全量构建。
- RateWaitMs、BackoffMs 统计限流与退避定时等待，不含网络耗时和普通锁排队。
- SaveAttempts、SaveSuccesses、SaveFailures、JsonBytes、SerializationMs、SqliteMs 保留既有口径；性能报告本身不计为业务保存。
- DurationMs、CancellationMs 表示执行时长和取消到退出的延迟。报告不包含凭据、授权头、筛选原值或请求正文；报告输出失败不改变业务结果。

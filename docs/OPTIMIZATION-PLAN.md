# 代码优化计划

本文列出优化时必须遵守的要求、已经完成的优化和后续方向。2026-09-29 的原计划及各步骤的详细做法保存在 [历史记录](history/OPTIMIZATION-PLAN-2026-09-29.md)。测量结果见 [性能报告](PERFORMANCE.md)。

## 不能改变的要求

以下规则来自 [API 支持情况](API-CONTRACTS.md)、[升级与恢复说明](STORAGE-MIGRATION.md) 和各轮测试报告，任何优化都不能违反：

1. **写入不自动重发。** 结果未知的写入只用 GET 核对；已有 ID 不再 POST。唯一例外（E7，D5，2026-11-12）：服务器肯定没有处理的写入（429，或请求没有发出）在本轮稍后再发一次，每条最多一次。
2. **回读确认。** 写入后必须重新 GET 并比对，通过后才算成功，并记录已验证的操作。
3. **限流预算。** 进程内所有 VA 合计每分钟最多 60 次请求，请求间隔至少 1 秒，遵守 Retry-After。
4. **判重和冲突检查。** 新建前查重，修改前读取远端最新状态，删除前检查引用。判重索引只有在完整读取成功后才能使用。
5. **保存顺序。** 请求发出前、收到响应后都要先保存进度；使用版本号防止旧数据覆盖；提交失败时不改变内存数据。
6. **兼容性。** CSV 字节格式、中英文提示、旧数据库升级（先完整备份）以及现有的禁用功能保持不变。

## 明确不做的优化

- 把限流预算提高到文档写的每分钟 100 次。这个额度由同一 VA 的所有客户端共用。
- 并行发送请求。预算按每秒 1 次串行执行，并行不会更快，只会增加 429。
- 直接用 POST/PUT 的响应代替回读 GET。
- 提前批量读取列表来做修改前的冲突检查。这样拿到的数据可能已经过时，冲突检查会失去意义。
- 写入失败后自动重试。
- GC 改用 `SustainedLowLatency` 模式。2026-11-22 试过，停顿次数和长度都没有变化，因为停顿来自 WinUI 要求的完整回收（见[性能报告](PERFORMANCE.md#gc-设置试验2026-11-22)）。
- 只打开 Server GC、不加限制。读取和审阅快 25–50%，但切换 5 次工作区后工作集多约 800 MiB，超过 100 ms 的停顿也没有减少。加限制的组合见后续方向第 6 项。
- 复用审阅页和列表，不每次替换页面。2026-11-23 试了两个原型（每个工作区只留一个审阅页；再保留同一个行集合、原地替换内容），WinUI 要求的完整回收照样发生，5 万行时提交前检查的最长停顿反而从 108–179 ms 变成 176–202 ms（见[性能报告](PERFORMANCE.md#复用审阅页的试验2026-11-23未采用)）。

## 后续方向

按预期收益排列。每一项都要先补充测量，并且完成后在同一台机器上记录修改前后的数据。切换工作区、完整保存和结构拆分已由重构完成，已从这里移除。修改前的数据见[性能报告](PERFORMANCE.md)中 2026-11-18、2026-11-20 的两节。

**审阅和提交前检查停顿的来源（2026-11-22 查明）。** 150–260 ms 的停顿是 WinUI 要求的阻塞式完整回收：触发点是 `ReferenceTrackerHost.DisconnectUnusedReferenceSources`，在审阅页替换大表格这类有大量界面对象可以释放的时候发生，产品代码里没有 `GC.Collect`。这次回收的暂停大致和存活的堆大小成正比，所以 GC 设置帮不上忙，要缩小审阅时还活着的数据。行数据已经缩小（见“已完成”2026-11-22），旧审阅页留下的那份计划也已及时清掉（见“已完成”2026-11-23），当前这一份计划的分配也已减少（见“已完成”2026-11-23 第三步），但它常驻的部分不大，5 万行时提交前检查仍有约 170–200 ms 的停顿，存活的大头是工作区行数据和界面对象。详见[性能报告](PERFORMANCE.md#内存诊断2026-11-22)。

**这次停顿作为已知成本接受（2026-11-23 决定）。** 复用审阅页的试验表明，这次回收不是由审阅页被替换引起的：第一次回收总是在数据页（带大表格）离开界面后约 0.4–0.6 s 出现，审阅页一次也不离开界面时照样发生。看起来是 WinUI 累计释放或新建了足够多的界面对象后才要求回收，具体阈值没有公开文档，是根据回收发生的时刻推断的。剩下能做的只有缩小回收时还活着的数据，例如相同的值共用字符串，估计只能再缩短 10–20 ms，不值得单独做。5 万行时 150–200 ms 的单次停顿（每次打开审阅页后的第一次提交前检查）不再作为阶段 7 的目标。阶段 7 第 3 项已完成（2026-11-23）。

1. ~~**审阅页只留一份计划。**~~ 已完成（2026-11-23）：第二份是 WinUI 还没释放的旧审阅页，现在离开或替换时先清空它。
2. ~~**审阅计划少复制数据。**~~ 已完成（2026-11-23）：每次提交前检查的分配降到原来的 1/3–1/5，年轻代回收大幅减少，但最长停顿没有下降。剩下的停顿是每次重新打开审阅页后第一次提交前检查里那次 WinUI 要求的完整回收，它的存活量主要是工作区行数据（5 万行约 70 MiB）和界面对象，计划和提交项只占约 29 MiB（其中提交项约 22 MiB，提交时要用）。复用审阅页已试过，无效（见“明确不做的优化”）；这次停顿已作为已知成本接受（见上）。见[性能报告](PERFORMANCE.md#审阅计划的分配2026-11-23)。
3. ~~**启动与读取工作区。**~~ 已完成（2026-11-23）：读取在后台进行并显示进度，读取本身 5 万行快约一半、分配降到约 1/5，常驻少 24 MiB（相同的值共用字符串一并做了）。比 R0 多出的分配是行初始化器复制字段字典，已随新的读取去掉。第一次启动慢查到是程序文件刚写入后的第一次加载（最可能是 Defender 扫描，未证实）。ReadyToRun 的评估结果（第一次启动快约 1.5 s、平时快 0.1–0.2 s、包大 50 MB）待用户决定是否采用。见[性能报告](PERFORMANCE.md#读取工作区2026-11-23)。
4. ~~**快照索引缓存。**~~ 评估后不做（2026-11-23）：审阅时扫描和验证各建一次快照字典，5 万行合计约 3.6 MiB 的临时分配，只占修改前固定开销的 7%；缓存会让每个资源的索引常驻（5 万行约 1.8 MiB），而完整回收的暂停与常驻量成正比。
5. **2 万行打开数据页的两簇耗时。** 约 310 ms 和约 420 ms，同一版本也会跳，原因未查明；先查明再说是否要优化。
6. **Server GC 加限制（可选试验）。** 只在前几项做完后仍有明显停顿时再试：Server GC 配合限制堆数量（`GCHeapCount`）或打开 `GCConserveMemory`，看能否保住大部分吞吐量，同时把多出来的内存压回去。这台机器有 22 个逻辑处理器，Server GC 实际建了几个堆没有核实。

## 检查方式

每一步都要通过全部自动测试和相关的窗口测试；涉及存储时，还要通过迁移测试和真实进程终止测试。完成后更新 [测试报告](TEST-REPORT.md)、[性能报告](PERFORMANCE.md) 和 [更新日志](../CHANGELOG.md)。

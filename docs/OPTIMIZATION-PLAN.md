# 代码优化计划

本文列出优化时必须遵守的要求、已经完成的优化和后续方向。2026-09-29 的原计划及各步骤的详细做法保存在 [历史记录](history/OPTIMIZATION-PLAN-2026-09-29.md)。测量结果见 [性能报告](PERFORMANCE.md)。

## 不能改变的要求

以下规则来自 [API 支持情况](API-CONTRACTS.md)、[升级与恢复说明](STORAGE-MIGRATION.md) 和各轮测试报告，任何优化都不能违反：

1. **写入不自动重发。** 结果未知的写入只用 GET 核对；已有 ID 不再 POST。
2. **回读确认。** 写入后必须重新 GET 并比对，通过后才算成功，并记录已验证的操作。
3. **限流预算。** 进程内所有 VA 合计每分钟最多 60 次请求，请求间隔至少 1 秒，遵守 Retry-After。
4. **判重和冲突检查。** 新建前查重，修改前读取远端最新状态，删除前检查引用。判重索引只有在完整读取成功后才能使用。
5. **保存顺序。** 请求发出前、收到响应后都要先保存进度；使用版本号防止旧数据覆盖；提交失败时不改变内存数据。
6. **兼容性。** CSV 字节格式、中英文提示、旧数据库升级（先完整备份）以及现有的禁用功能保持不变。

## 明确不做的优化

- 把限流预算提高到文档写的每分钟 100 次。这个额度由同一 VA 的所有客户端共用。
- 并行发送请求。预算按每秒 1 次串行执行，并行不会更快，只会增加 429。
- 直接用 POST/PUT 的响应代替回读 GET。
- 提前批量读取列表来做修改前的冲突检查。这样拿到的数据可能已经过时，冲突检查会失去意义。
- 写入失败后自动重试。

## 后续方向

按预期收益排列。每一项都要先补充测量，并且完成后在同一台机器上记录修改前后的数据。

1. **切换工作区只保存待写的单元格编辑。** 现在切换前会完整保存整个工作区：5 万行时离开工作区约 2.4 s，每轮还会增长约 6 MiB 原生内存。按代码中的约定，除单元格编辑外，其他改动发生后都会立即完整保存，所以切换时只需要 `SaveEdits`。前提是逐一确认所有修改数据的入口都遵守这个约定，否则会丢数据，需要单独决定是否修改。
2. **审阅计划少复制数据。** 5 万项变更时，构建计划约分配 250 MB，GC 暂停仍会让界面停顿约 0.3 s。可以让计划只保存变化字段的前后值，按需再读取整行。
3. **启动与读取工作区。** 读取工作区目前在界面线程上同步进行，5 万行时约 1.1 s，分配约 530 MB。可以改为后台读取并显示进度，并为行 JSON 使用 System.Text.Json 源生成，同时复用重复的字段名和常见值字符串。可另外评估 ReadyToRun 对冷启动的帮助，代价是包体会变大。
4. **完整保存。** 序列化在界面线程上进行，再先删除后重新插入全部行。可以先在界面线程上捕获不可变数据，再在后台序列化；按内容哈希只写入变化的行。
5. **快照索引缓存。** `Snapshot.ToDictionary` 在计数、查询、规划和校验中被反复构建，可以像草稿位置索引一样缓存。
6. **可维护性。** 字段规格表已在 R2 建立；`OperationsAdapter.Plan` 和 `OperationsBatchExecutor.ExecuteCoreAsync` 的拆分继续按重构计划 R5 推进，保持请求与回读行为。
7. **测试脚本。** 修复 `test-localization-ui.ps1` 在“Apply to drafts”处的失败；把脚本改为带 BOM 的 UTF-8 或避免使用中文字面量，使其在 Windows PowerShell 5.1 下也能运行。

## 检查方式

每一步都要通过全部自动测试和相关的窗口脚本；涉及存储时，还要通过迁移测试和真实进程终止测试。完成后更新 [测试报告](TEST-REPORT.md)、[性能报告](PERFORMANCE.md) 和 [更新日志](../CHANGELOG.md)。

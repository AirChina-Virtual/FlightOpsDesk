## 两个偶发失败的窗口测试改稳（2026-11-23）

分支 `test/flaky-window-tests`，基于 3907798。只改测试和 QA 验证命令（`tests/UiVerification`，只编进 QA 包），没有改产品代码。日志在 worktree 的 `artifacts/scratch`（不在仓库里）。

**机队提示测试（`ConnectedDialogTests.The_fleet_cell_names_an_unapproved_fleet_on_hover_until_every_fleet_is_approved`）。**

- 原因。留下的两次失败日志（`artifacts/ready-to-run/ui-all-2.log`、`artifacts/workspace-load/ui-all-2.log`）都不是找不到 tooltip，而是同一处 `Sequence contains no matching element`：第三次在机型框里切换 Fleet 6 之后，等待“航线机队变为 4”时，查找航线 CAO100 的 `Route()` 抛了异常。前一步“悬停时显示提示”的断言已经通过。`Route()` 先用 UI 自动化数出窗口里的行数 N，再经 QA 管道逐个读前 N 行（`data-row:0…N-1`），没有 CAO100 就直接抛出；它在 `Until` 的条件里，而 `Poll` 只把元素失效一类的异常当作“再等等”，所以这一次读不到就让测试立刻失败，不会等表格刷新完。两种行号来自两个地方，QA 管道一次一行地读，中间界面线程可以刷新表格。
- 没有复现出具体是哪一瞬间读不到：在改好的测试里临时记录每次读取（单独 3 次、CPU 全核占满 3 次、整类 2 遍），以及点“应用”后 3 秒内 UI 自动化看到的行数（3 次切换各采样一次）和对话框打开时的行数，都是 3 行、都能找到 CAO100。所以“读不到”是短暂的，只能从失败栈确定在哪里失败、为什么一次就失败。
- 另一处外部依赖。`AppWindow.OpenToolTip()` 原来在整个桌面上找第一个 tooltip。临时记录显示，悬停之前它就一直返回“有 tooltip”：本机另一个程序（Antigravity 编辑器）在 UI 自动化树里一直留着一个 tooltip（它的快捷键提示，UI 自动化报告为在屏幕上，整个测试过程都在）。哪个程序的 tooltip 排在前面就读哪个，排在前面的不是本程序时，本程序的提示就“看不到”。2026-11-19 记下的“看不到 tooltip”没有留下日志，不能确认是不是这个原因。
- 改法。新增 QA 命令 `data-row-find:字段=值`，在界面线程上一次找出显示中的行，找不到返回 `{shown:false}`；`data-row` 和它共用 `DataRowState`。测试里的 `Route()` 改用它，找不到就返回 null；各项检查写成 `RouteShows(...)`，航线暂时不在时继续等，不会把“没有这一行”当成“没有提示”而提前通过。航线一直不出现时按超时失败，状态里写明“route CAO100 not shown”和读空的次数。`OpenToolTip()` 改为实例方法，只找本程序进程的 tooltip；`FleetHintSweepTests` 同样改用它。
- 不再依赖顺序。临时把 `FleetHintSweepTests` 的用例放回 `ConnectedDialogTests`（也就是 11-19 出问题的排法），整类 15 项连续 2 遍通过，之后已撤回。xUnit 的顺序是固定的，所以又把这个用例分别紧接在 `FleetHintSweepTests` 和 `ConnectedDialogTests` 的其他 13 个用例之后各跑一次（各自一次 `dotnet test`，保留前一个用例留下的指针、前台窗口等桌面状态），14 次都通过。`FleetHintSweepTests` 仍放在自己的类里：它测的是指针输入和窗口不崩，不是连接后的对话框；类注释已改为这个理由。

**数据页的“未应用条件”（`DataInteractionTests.Density_query_batch_lock_layouts_and_review_work_with_many_rows`）。**

- 原因（在 ReadyToRun 一节已记）。QA 命令 `data-unapplied` 写入搜索框后 `await Task.Delay(50)` 再读，而搜索框在停止输入 300 ms 后自动应用条件；界面线程在这期间卡住超过 300 ms，计时器的 Tick 就可能先于这次读取执行，读到“已应用”。另外，应用一旦开始，下一条命令 `data-query` 会因为查询进行中（`gate.CanStartQuery` 为假）直接返回、不执行。
- 改法。`data-unapplied` 先挂一个只用一次的 `TextChanged` 处理，再写入文字。程序自己的处理先订阅、先执行：显示“条件未应用”并启动 300 ms 计时器；同一次调度里接着执行这个处理，读出状态并记下计时器是否已启动，然后停掉计时器，再返回。计时器在这次调度之后才可能 Tick，所以无论界面线程多忙，读到的都是刚输入时的状态；停掉计时器避免它和下一条 `data-query` 抢着查询。测试新增一条断言：输入确实启动了自动应用的计时器（`autoApplyArmed`），原有断言不变（标为未应用、查询次数和总行数不变）。
- 同一类里其他固定等待。`data-density`（80 ms）、`data-window`（100 ms）、`data-scroll`（50 ms）、`data-screenshot`（250 ms）等待后读的是布局结果，前面都有 `UpdateLayout()`，没有会改变被断言状态的计时器；界面线程卡住只会让等待变长，不会读到别的状态。窗口大小变化是异步的，但断言（密度、每页 200 行、未应用）不依赖窗口大小，只影响截图。所以没有改。

**验证。** 正式包和 QA 包从这个分支重新生成（ReadyToRun），各自先跑的 `check-all.ps1` 都全部通过：Release 构建 0 错误、没有新增警告、单元测试 1,939、集成测试 767 通过 1 跳过。

- 机队提示测试单独连续 10 次通过；加上第一次和上面 14 次接在其他用例后面的，单独运行共 25 次，全部通过。
- 数据页测试（2 万行、5 万行两项）单独连续 10 次通过，加上第一次共 11 次，22 项全部通过；5 万行那次 `autoApplyArmed` 为真、标为未应用、总数 50,000、查询次数不变。
- 全部普通窗口测试（`--explicit only --filter-not-trait Category=Measurement`，64 项）：用这两个包完整跑了 2 遍，都是 64 项全部通过（6 分 01 秒、6 分 20 秒）。`ToolbarTests` 两遍都没有因为真实鼠标点击没生效而失败。
- `pwsh scripts/check-all.ps1`：全部通过（Release 构建 0 错误、没有新增警告、单元测试 1,939、集成测试 767 通过 1 跳过）。

**没有验证的。** 没有复现出原来那次失败的具体瞬间（见上）。没有用改动前的测试在同样条件下多跑几轮来对比失败率。`Category=Measurement` 的测量和 `DataPerformanceTests` 没有重跑。

## 后台读取工作区、缩短读取（2026-11-23）

阶段 7 第 3 项。分支 `perf/workspace-load`：3cce927（测量）、5e71647（后台读取）、a89b46b（缩短读取）、1f9e975 和 ac1e23a（窗口测试驱动与测量修正）。修改前的对照是 669a249 加上同一份测量代码（单独的 worktree，未提交）。原始数据在 `artifacts/workspace-load`。

**测量方法。** 存储的读取现在可以带一个观察者，报告每一步和已读行数（窗口用它显示进度）。新基准 `--benchmark-load-stages` 用窗口基线的 2 万／5 万行工作区（`DataUiFixture.Seed`，全字段航线、20 步撤销），每种读 5 次，记录每一步的耗时和读取线程上的分配；行这一步再单独拆成“SQLite 读出 JSON 文本”和“文本转成行”，另用 R0（bd6c831）的行结构解析同一批文本作对照；再用 `AllocationTick` 事件按类型抽样一次读取的分配。窗口里 QA 包新增：启动时第一次读取的耗时和工作区显示出来的时刻，以及切换工作区（从数据页和从工作区页）时界面线程的最长停顿。

**修改前各阶段（5 万行，5 次中位数；2 万行在括号里）。**

| 阶段 | 耗时（ms） | 分配（MiB） |
|---|---:|---:|
| 打开连接、头部、任务、元数据 | 8（4） | 0 |
| 读取行（SQLite 读文本＋转成行） | 1,085（415） | 599（240） |
| 　其中单独做：SQLite 读出文本 | 143–218（56–74） | 110（44） |
| 　其中单独做：JSON 转成行 | 714–954（305–362） | 487（195） |
| 未改的草稿行共用快照行 | 10（5） | 0 |
| 撤销历史读取、校验 | 4（2） | 4（2） |
| 草稿索引 | 2（1） | 2（1） |
| journal 基线 | 0 | 1（0） |
| **合计** | **1,110（427）** | **606（243）** |

5 万行按类型抽样：字符串 262 MiB（每行 JSON 文本约 2 KB 的 UTF-16 字符串、每个字段名和值各一个字符串）、字典条目数组 210 MiB、桶数组 48 MiB、System.Text.Json 的读取栈 44 MiB、字典对象 24 MiB、枚举器装箱 6 MiB。

**比 R0 多出的分配。** R0 的行是可写属性，反序列化出来的字段字典直接留在行里。R2 起行改为只读，`Fields` 的初始化器把反序列化出来的字典再复制一份（精确容量的新字典，加上一个装箱的枚举器）。同一批文本按 R0 的行结构解析分配 407 MiB，按现在的行解析 487 MiB，差的约 80 MiB 就是这次复制（2 万行 163 对 195 MiB）。核心基准 `--benchmark-core-load` 多出的 80 MiB（421→501）也是它。

**启动时读取占多少。** 修改前读取在窗口构造函数里同步进行：5 万行时非首次启动从进程开始到构造结束 2.27–2.54 s，其中读取 1.70–1.91 s（启动时 JIT 还没做完，比单独读取的约 1.07 s 慢）；首帧 2.53–2.78 s。2 万行时读取 1.05–1.10 s，首帧 1.84–1.88 s。

**改了什么。**

- 后台读取：启动、切换工作区、检查点写入失败后的重新读取都在后台线程执行 `storage.Load`。`WorkspaceSession` 在读取期间持有保存锁（保存和任务检查点都要等），并进入新的门控状态 `WorkspaceLoading`：编辑、导航、工作区和资源选择、命令、独占工作、任务、查询、在线请求和自动保存都不能开始。窗口用读取面板盖住页面（进度环、“正在读取工作区…”和已读行数，中英文），等新工作区放好并 `Render()` 之后才撤下。启动时窗口先显示，首帧只有这个面板，导航和选择器都不可用。读取失败时保留当前工作区，提示与以前相同（启动时仍是启动错误窗口），工作区选择器回到当前工作区。读取期间关闭窗口会先提示，读取完成后照常保存并关闭。读取期间在选择器里再选别的工作区不执行，选择器回到当前工作区。切换时运行中的在线任务的处理不变：任务运行时本来就不能切换工作区。
- `storage.Load` 在后台线程上是安全的：每次读取打开自己的连接，在一个只读事务里读完（WAL 模式）；读取时持有 `saveLock`，所以不会与保存或检查点写入同时进行；字段名共用表是线程局部的，在同一线程上开始和结束；读出的工作区在放进会话之前别人看不到。
- 缩短读取：行的 JSON 直接以 SQLite 存的 UTF-8 字节读出（`RowTextReader`，在读取自己的连接和事务里用 SQLitePCL 的语句，不再先转成 .NET 字符串）；程序写出的那种形状由 `DataRowJson` 直接读进行自己的字段字典（字段名照旧共用；同一次读取内相同的值共用一个字符串）。其他任何形状（多余或缺少的属性、重复的名字、空值、无效 UTF-8 等）照旧从数据读取器会得到的那个字符串用通用的反序列化读取。没有改用 System.Text.Json 源生成：它仍会建一份中间字典再复制，省不掉最大的两块。

**修改后各阶段（5 万行；2 万行在括号里）。** 合计 390–575 ms（133–250 ms），分配 111 MiB（42 MiB），其中读取行 369–550 ms、104 MiB（125–231 ms、39 MiB）；其余各步不变。读取后常驻托管内存 73→49 MiB（29→20 MiB），一次阻塞式完整 GC 61–91→36–49 ms（19–29→13 ms）（`--benchmark-memory-load`）。相同值共用一个字符串单独看：常驻少 24 MiB，分配少 41 MiB，读取不变慢，所以采用了。

## 审阅计划少复制数据（2026-11-23）

阶段 7 第 2 项。先分阶段量清楚审阅时的分配来自哪里，再去掉其中不必要的部分；审阅的结果一项都不变。

**测量方法。** 新基准 `--benchmark-review-stages`（`tests/VamSys.Benchmarks`）：窗口基线那样的 5 万行工作区（全部是带全字段的 jumpseat 航线），前 N 行改 Remarks（与 `review-bench` 相同），分别量 0、1 千、5 万项变更时各阶段在当前线程上的分配量，以及建好后留着的计划、提交项、行视图模型各占多少（强制完整 GC 后的差值）。Online 模式给行加上远端身份，经真正的 `OperationsAdapter.PreviewPlan` 预览（传输层拒绝发送请求）。窗口基线 `review-bench` 用的是 **Demo** 模式（`DataUiFixture` 建的工作区是 Demo），所以窗口里没有在线预览这一块。窗口基线里 `review[0..2]` 分别是 1 千、1 万、5 万项变更。原始数据在 `artifacts/review-alloc`（`stages-before/after.*`）。

**修改前的来源（6292ec1）。** 0 项变更时只有扫描（约 1.9 MiB，快照字典），验证整个跳过。只要有 1 项变更，验证就要扫整个资源：5 万行时约 46 MiB，这就是窗口里每次提交前检查约 50 MiB 的固定开销。再拆开：按“出发／到达／签名”分组找疑似重复的新建占 27 MiB，其中每个 jumpseat 的签名都做一次 JSON 序列化（17.6 MiB），而这一组只用来标记没有键的行，5 万行里一行都没有；按键分组找重复 5.2 MiB；逐行检查 7.6 MiB（每个引用字段 `Split` 出一个数组、`IReadOnlyList` 的枚举器装箱）；键缓存 3.9 MiB（ID 本来就是规整的文本，缓存不省任何复制）；快照字典 1.8 MiB。与变更数成正比的部分：每项提交项约 940 B（其中 4 个空列表、一份每次都重新格式化的默认消息），在线模式下每项变更再建一个临时 `ChangeItem`（约 1.2 KB，默认构造还多建一个空行和一个空字典），内容键里每行排序都新建一个比较委托（约 120 B）。

**改了什么。**

- 验证（`Schemas.Validate`）：先用一个集合判断有没有重复键，有才按原来的代码分组列出；只有存在“未删除且没有键”的行时才计算签名分组；单个引用（不含逗号）直接取去掉空白的文本，结果与按逗号拆分相同；引用字段用下标循环。`ValidationPass.Key` 只缓存需要复制才能得到的键（去空白或转大写后与原文不是同一个字符串的），其余每次重新算，结果相同。
- 在线预览、操作键和证据：没有现成提交项的变更，共用一个临时 `ChangeItem` 和字段字典，每项变更重新填入；它不返回、不放进计划。预览、`ApiOperationPolicy.Key`、`IndependentApiEvidence.Covers` 只在调用期间读取它（已查过不写入、不按对象保存）。`ReviewPlanBuilder` 的说明里写明了预览不得保留或修改这个对象。
- `ChangeItem`：`Dependencies`、`ApiSteps`、`RecoveryCandidates`、`VerificationDifferences` 改为第一次读取时才创建；默认消息只格式化一次。保存出来的 JSON 不变（没碰过的列表仍写成 `[]`）。`PlannedChange.ToItem` 只在有依赖时才设置依赖列表。
- 内容键排序改用缓存的 `string.CompareOrdinal` 委托（同一行的字段名互不相同，排序结果与原来一样）；`ChangePlanner` 里同一批编辑的变更共用一个字段名数组（引用解析时会换成新数组，不会互相影响）；`BuildForWorkspace` 的变更行集合预先定好容量。
- 没有做快照索引缓存（后续方向第 4 项）：扫描和验证各建一次快照字典，5 万行时合计约 3.6 MiB，只占修改前固定开销的 7%；缓存下来反而会让这 1.8 MiB 一直存活，而停顿正是和存活量成正比的。

## 离开或替换审阅页时释放旧页的数据（2026-11-23）

审阅页被替换（重新打开、提交前检查发现内容变了、移除未获准机队后刷新）、切到其他页、或备份并清空工作区时，窗口调用 `ReviewViewModel.Release()`：清掉计划和行，发一次全属性通知让列表的 `ItemsSource` 换成空列表，提交和处理冲突按钮不再可用，之后才到的计划也不再显示。同时 `ReviewService.Shown` 一并丢弃：它只在审阅页上的提交（`CurrentReviewPlan`）和 QA 状态查询里读取，新打开的审阅页会显示自己的计划。`ConfirmWorkspaceSubmission` 读的 `shownReviewPage` 始终是当前页，释放的只有旧页。

- 新单元测试（`ReviewViewModelTests`，3 项）：释放后行为空、不可提交或处理冲突、既不是“准备中”也不显示计划，只发一次全属性通知，重复释放不再通知；释放后才到的计划不显示；释放后计划和行可以被回收（`WeakReference` 加强制 GC）。

## 读取工作区时共用未改的行和字段名（2026-11-22）
